# Winning the coding section: many accepted tasks, fast

Companion to `../SKILL.md`. That file says what a valid task is; this one says how to make tasks that get accepted and how to make many. Cheating attempts (deleted tests, skip configs, hardcoded outputs) are covered in `~/.claude/skills/frist-hackathon-playbook/references/non-lazy-judges.md`; this file is about tests that reject *honest wrong fixes*. Ready-to-paste role prompts: `role-prompts.md`. Script: `../scripts/mutation_bar.py`.

## The core problem, and what the evidence says

"Agents are bad at writing tests, good at passing their own bad tests." The literature agrees and points at the fix.

- **LLM tests encode what the code does, not what it should do.** Oracles generated by LLMs mostly capture the actual implementation's behavior, so a test written while looking at buggy code asserts the bug. https://arxiv.org/abs/2410.21136
- **Coverage is not strength.** One LLM suite hit 100% line and branch coverage with a 4% mutation score; feeding mutation results back raised scores to about 89%. https://arxiv.org/html/2506.02954v6 . MuTAP re-prompts with surviving mutants and reaches 93.6% mutation score. https://arxiv.org/abs/2308.16557
- **Weak tests let wrong fixes through, even on curated benchmarks.** UTBoost: 28.4% of "passing" patches on SWE-bench Lite and 15.7% on Verified were wrong. https://arxiv.org/abs/2506.09289 . PatchDiff: 29.6% of plausible patches behave differently from the reference (about 11% truly wrong), found by generating tests that *differentiate* the candidate from the reference patch; flaky tests filtered over 20 runs. https://arxiv.org/abs/2503.15223
- **Mutation-first generation works in production.** Meta ACH generates faults for a specific concern, then tests that kill them; engineers accepted 73% of its tests; an LLM equivalent-mutant detector got 0.79 precision / 0.47 recall, 0.95 / 0.96 with simple preprocessing. https://arxiv.org/abs/2501.12862 . TestGen-LLM only keeps tests that build, pass repeatedly (flake filter) and add coverage; 73% accepted. https://arxiv.org/abs/2402.09171 . Note the lesson: filters, not trust.
- **Visible-suite success hides holdout failure.** SpecBench: frontier agents saturate the visible suite but reward hacking and gaps persist on holdout suites. https://arxiv.org/abs/2605.21384 (abstract only read)
- **Test-based verifiers have low distinguishability** between good and bad patches. https://arxiv.org/abs/2504.07164 (R2E-Gym, abstract)
- **Property-based tests written by an agent find real bugs**, but need validation: 56% of the agent's PBT bug reports were valid. https://arxiv.org/abs/2510.09907 . CodaMosa (ICSE 2023) used LLMs to push coverage past plateaus, which is the wrong target for us (from memory, not re-read).
- **Frist already grades this way.** Their blog: "Browser journeys and backend calls compare 155 facts with values from the working site", journeys replay on held-out inputs, and failing models "test only the ticket's example" (GPT-6 Sol) or write sub-agent tests that "confirm its assumptions" (GPT-6 Astra). Text from the frist.ai bundle (https://frist.ai/assets/index-B8qLCGFE.js, post "Green Tests, Broken Apps", read Nov 14). So: **differential testing against the working original on held-out inputs is the house style.** Match it.
- **ProgramDistill (cited by Frist as their method)**: a mask is accepted only if the app builds, all prerequisite journeys still replay, and the target journey fails; a separate LLM "mask-depth critic" rejects superficial masks (toggling a feature flag, deleting a call site but leaving the implementation); the problem statement withholds the implementation and the exact verification signals; grading traces stay outside the agent container. https://arxiv.org/abs/2609.18805 (PDF at https://microsoft.github.io/debug-gym/static/papers/ProgramDistill_arxiv.pdf, sections 2.2 to 2.3)

Our advantage: **we hold the working original.** It is a free, perfect oracle. The test author never has to guess expected values; it records them.

## Bug-site selection

Run once per clone (one catalog agent, before any task worker). For every user journey on the clone, list its decision points and score each:

| Check | Keep if |
|---|---|
| User-visible | Wrong output shows in the page or an API the page calls |
| On a journey path | Reachable by clicks from a route, so a browser journey can see it |
| Generalizes | Manifests on many records, not only the ticket's example, so held-out inputs catch hardcoding |
| Cross-layer | Symptom in UI, cause in API, query or shared helper (2+ files to trace) |
| One right answer | The original's behavior is the only reasonable reading of the ticket |
| Quiet | Type checker, build, lint and existing tests stay green after planting |
| Isolated | Neighbouring journeys still pass, so P2P is green on the broken repo |

Decision-point types to look for: record lookup (id vs index vs name), fallbacks (`??`, default branch), filters (WHERE clause or ORM `where`), sort and tie-breaks (ORDER BY / `orderBy`), pagination (LIMIT/OFFSET, `skip/take`), boundaries (`<` vs `<=`, inclusive end dates), aggregation (subtotals, counts, badges, balances), formatting (cents, dates under the app's clock, pluralization), state transitions (status machines, cancel, undo), cache invalidation (query keys, refetch after mutation).

Aim for 15 to 25 sites per clone (feature area = route or router file). Each worker takes one site from a different area.

Before cataloguing, on any unfamiliar app: boot it, walk every journey, and list what is already broken (the open-source app used in the Nov 14 dry run crashed on boot and had 13 broken or misleading journeys). Only catalogue sites whose journey works on the original. Check whether the ORM or schema file is actually used (that app shipped a `schema.prisma` but ran raw SQL on sql.js), how state persists, timestamp resolution, and whether the original itself is nondeterministic anywhere (random ids deciding an order).

## Bug taxonomy (React/Vite web app with an API and a database; examples use Prisma or raw SQL)

Good (findable from the ticket, needs tracing, single fix):
- **Wrong record resolution.** Bag line priced from the product's first colour while the picture uses the chosen colour (`priceVariant(product, findVariant(product, line.colour))` where the cart stores `variantId`). Symptom on `/bag`, cause in the API helper.
- **Dropped fallback.** Restaurant without its own stored profile shows an empty page instead of falling back to the catalog record.
- **Query filter slip.** Prisma `where: { status: { in: ['OPEN','PENDING'] } }` loses `PENDING`; pending reservations vanish from "Upcoming".
- **Pagination seam.** `skip: page * size - 1`: page 2 repeats page 1's last item. Visible only with enough records, so held-out data catches it.
- **Tie-break.** Sort by price with no secondary key in the API but the UI expects name order on ties; results reorder between loads. Only plant this if the original has a deterministic tie-break to restore.
- **Boundary.** Time slots exclude a reservation ending exactly at closing; sale price equal to list price shows a strike-through.
- **Stale cache after mutation.** Cancel succeeds server side, but the list query key is not invalidated, so the item stays until reload. Journey: cancel, go back, check list.
- **Feature removal (logic only).** Keep the button and label, remove the handler and the endpoint body (ProgramDistill's logic-only mask). Ticket is a feature request.
- **Raw SQL shapes** (from the dry run): a UNION ALL whose second SELECT has correct-looking aliases in the wrong column order (settlements applied backwards); a soft-delete filter on the wrong column (`delete_reason IS NULL` instead of `deleted_at IS NULL`, so only one of two delete paths is excluded); an aggregate recomputed from the stale row (`computeSplits(e.amount_cents, ...)` after the UPDATE).
- **Combined bug** (SWE-smith "combine"): two small validated bugs on one journey, e.g. wrong lookup plus stale subtotal. Raises difficulty without ambiguity.

Bad (likely rejected or useless for training):
- Syntax or type errors, failed builds, crash on load with a stack trace pointing at the line.
- A greppable marker: commented-out code, a feature flag, `hidden` prop, `TODO`, a suspicious name. ProgramDistill's critic rejects flag toggles and call-site deletions for this reason.
- Bugs only in console output, logs or styling.
- Bugs that live in seed data (the "fix" is editing data; held-out data makes the task meaningless).
- Bugs visible only for the ticket's example record (hardcoding the example passes).
- Ambiguous targets: "sort is wrong" when several orders are defensible, rounding mode not stated, timezone not pinned.
- Anything touching wall-clock time, randomness or network.

## Ticket writing

Use Frist's template (see SKILL.md). Rules:
1. **Symptom, not cause.** What the user did, what they saw, what they expected. Never the file, function, variable, layer, or the word that names the bug ("fallback", "index", "cache key").
2. **One concrete example with exact values** (Frist states "every value the checks look for"), then **a generalization sentence**: "This must hold for every shoe, colour and quantity." The example lets the solver reproduce; the sentence tells them hardcoding fails.
3. **Pin every rule that held-out inputs exercise**: ties, empty states, rounding, inclusive or exclusive ends, what shows when data is missing. If the tests check it, the ticket implies it.
4. **Do not paste test assertions or test names.** SWE-smith found issue text that revealed the tests cut reproduction attempts from 379 to 127 of 500 runs. Fixed templates also made solver behavior homogeneous (6.4% vs about 7.7% downstream resolve). Vary the voice: customer report, PM request, QA note. https://arxiv.org/html/2504.21798v2
5. **Grep test.** For each distinctive noun phrase in the ticket, `grep -rn` the repo. If any phrase lands within a few lines of the bug, reword.
6. **Stranger test.** A fresh agent reads only the ticket and states the expected behavior for three held-out inputs. If it disagrees with the original app, the ticket is ambiguous. SWE-rebench keeps an issue only if three independent LLM judges rate it adequately specified (https://arxiv.org/abs/2602.23866, search summary, unverified detail).

## Test-strength recipe

The test author gets the ticket and the original code, never the bug diff, never the broken repo.

1. **Differential vs original (main check).** Write a fact recorder that drives a journey and returns normalized facts: visible text of named elements (`data-testid`, labels), API JSON the page uses, DB rows after a mutation (or the API that exposes them when the DB is not readable, e.g. in-memory sql.js). Run it on the *original* app over **held-out inputs** (records, quantities, dates the ticket never mentions, including every boundary the ticket implies) and save the result as `golden.json`. The hidden test replays the same journeys on the candidate and compares facts. Fresh DB, `TZ=UTC`, and the app's clock anchored (fixed start plus elapsed, shared by backend and browser). Do not freeze it: a frozen clock makes every `created_at` equal and breaks ORDER BY.
2. **Compare contracted facts only.** Labels, values, counts, order where the ticket fixes it. Not CSS classes, internal ids, timestamps or field order. Over-specific facts reject valid alternative fixes. Also drop facts that look like existing bugs or placeholders unrelated to the ticket.
   - **Record goldens twice.** A fact that differs between two reference runs is app nondeterminism (dry run: which member gets the leftover cent depended on random split ids). Replace it with its invariant (sum, multiset, floor/ceil) and pin that with a property.
   - **Relative rules are tested differentially inside one run.** "Exactly as if the expense had been added fresh" became: build a control group that adds the final state fresh and assert it equals the edited group.
   - **Contract surface.** The bug author states which surfaces tests may read (UI, API, DB). A wrong fix whose flaw is only visible elsewhere (e.g. inverted rows in a table no API exposes) is out of scope, not a test gap.
3. **Properties from the ticket.** Invariants any correct fix satisfies, checked over the same inputs: strike-through only when the price is lower, line totals sum to the subtotal, pages never repeat items, a filtered list is a subset, sort order holds.
4. **Neighbour regression journeys (P2P).** Same page and same API, other features. Their facts must avoid the ticket's code path so P2P passes on the broken repo and on the fix. These catch fixes that rewrite neighbouring behavior, Frist's top failure mode (36% of failed rounds broke something the app already did).
5. **Mutation bar** (`mutation_bar.py`), all required:
   - null (broken repo) fails, reference passes;
   - every **wrong fix** from a separate agent is killed (100%): example hardcode, fix in one layer only, rewritten fallback, boundary slip, neighbour regression, fix that masks bad data in the UI;
   - every **alternative valid fix** passes (tests not over-fit);
   - **auto operator mutants** of the reference in the touched files: at least 80% killed after excluding equivalents, each survivor either killed by a new check or justified in `equivalent_mutants.txt`.
6. **Determinism.** Reference passes 3 runs (`verify_task.sh`), plus Frist's own null/oracle rule.

BuddySplit (github.com/toxic-jpg/BuddySplit, React/Vite + Express + sql.js), shallow clone, 3 planted bugs, every role a fresh isolated subagent, 8 wrong fixes per bug from a separate agent, results from the clean rerun (one candidate at a time).

### Hardening rounds on the same app (Nov 14 night): what did NOT make tasks hard

Same BuddySplit clone (about 4,000 lines; backend about 900). Solvers: headless `claude -p`, 2 Opus 5.5 + 2 Fable 5.2 per task, ticket + broken repo only, transcripts audited clean. Every design below was solved by every solver.

| Design (lever) | Solves | Minutes |
|---|---|---|
| R1 two linked causes: server re-adds payer on create + standalone UI effect re-ticks payer (masked) | 4/4 | 3.0 to 11.2 |
| R1 deeper layer: schema default `CURRENT_DATE` on created_at (order symptom on 3 pages) | 4/4 | 1.4 to 3.5 |
| R1 removed logic: cross-group expense ownership removed at 5 points in 2 files | 4/4 | 2.0 to 4.0 |
| R2 removed logic: soft-delete honoured nowhere (6 points, 4 files, incl. a JS skip in a lib) | 1/1 screen | 1.5 |
| R2 two linked causes that CANCEL: UNION ALL column order books payments backwards + Settle button posts from/to swapped, so the UI path looks right | 4/4 | 1.1 to 2.1 |
| R2 deeper layer + SQL semantics: shared FROM helper used by 4 readers in 3 files, `LEFT JOIN` cancelled by a WHERE on the joined table, plus a balance-engine guard that drops rows of departed members | 4/4 | 2.4 to 3.0 |
| R2 logic-only feature removal across 2 layers: edit handler reduced to checks + pencil prefill removed; 15+ stated rules to rebuild | 4/4 | 2.8 to 3.5 |

How the solvers won, read from their transcripts:
1. **They read the whole backend first.** Turn 2 is typically `cat` of every route and lib file. On a small app, any backend cause is in context before the solver forms a hypothesis, so camouflage (L1), SQL semantics (L5) and "a layer deeper" do not hide anything: Opus recognised `LEFT JOIN ... WHERE pm.group_id` and UNION positional mapping on sight.
2. **They grep every ticket noun and read every hit.** `grep -rni settle` printed the swapped Settle line. Any cause on a line that carries a ticket noun, label, field or route word is found in the first minute.
3. **They implement every stated rule exactly.** Response codes, error bodies, partial-delete counts, split-type quirks, out-of-scope quirks: all honoured. Fairness forces us to state every tested rule, so stated traps are not traps.
4. **They verify the path the ticket's acceptance criteria name**, through the API and often Playwright. A masked cause on a path the criteria mention is found; even cancellation masking failed because the generalization named the Settle button.
5. Fable 5.2 was as strong as Opus 5.5 here (equal solve rate, similar or shorter times). The one 11-minute run was Fable.

So on a clone this size, planting did not reach a mixed solve rate with a fair ticket. That is why the playbook's difficulty gate records the screen and submits anyway. If staff or a rejection say difficulty matters, what is left, untested here: scale (a bigger clone where the relevant code does not fit in one read), fragmentation across many files the noun-grep does not reach (aim for 8+ edits in 5+ files), UI-heavy logic-only feature removals whose details only show when the page is driven, and runtime-only behaviour (state across reloads, live updates between two sessions, pagination with more rows than one page). Screen every candidate with ONE Opus run (below) and record the result; it does not decide whether the task ships.

### Large codebase round (Nov 15 night): size alone did NOT make tasks hard

Karakeep (github.com/karakeep-app/karakeep, shallow clone in `~/Hackathons-local/frist/large-app/`) is about 160k lines of TS (web 50k, tRPC backend 33k, mobile 24k, workers 13k, shared 11k): Next.js + tRPC + Drizzle/SQLite, with 558 green vitest API tests that run on an in-memory DB in 8 s. `pnpm install --filter` (trpc + web only) installed it in 30 s. I planted three fair bugs, each quiet (typecheck, lint, format and all 558 tests still green). Each got one headless Opus 5.5 screen (ticket in the prompt, cwd = broken repo); all transcript audits were CLEAN:

| Plant (lever) | Opus screen |
|---|---|
| Runtime ordering: the oldest-first ORDER BY tie-break was flipped to `asc(id)` while the cursor still assumes `desc(id)`. Bookmarks are only skipped or repeated when more of them share a save second than fit on one page | solved, 1.8 min |
| Fragmented: the blank-title fallback was lost at 4 sites in 4 files (3 SQL row mappers, plus a shared helper reached through the public list), dressed as a `?.trim() \|\|` to `??` refactor | solved, 3.7 min |
| Deep shared recursion: the smart-list loop guard mutates one shared visited set instead of copying it per branch, so the second branch that reaches the same nested list gets nothing | solved, 1.9 min |

None failed or took over 10 minutes, so no extra runs were made. What the transcripts show:
1. **On a big repo they do not read everything, and they do not need to.** They turn the symptom into a guess about what the faulty code looks like and grep for that shape, not for ticket nouns. The blank-title solver's FIRST call grepped `title ??`; the pagination solver grepped `sortOrder|cursor`; the smart-list solver grepped `visitedListIds` on its third call.
2. **A fair ticket names the kind of bug.** "Skipped or repeated across pages when many share a save time", "an empty title must behave like no title" and "two lists built on the same list" each point at one well-known bug shape (cursor tie-break, `??` vs `||`, a shared visited set). Fairness makes us state every tested rule, and that statement gives the shape away.
3. **A fast in-process test suite helps the solver.** Every solver wrote a vitest repro within its first few calls (in-memory DB, seconds per run). A runtime-only symptom stays easy when 10 lines of test can rebuild that state.
4. **Spreading the cause over files that each have their own surface does not slow them.** The ticket had to list the 4 surfaces, and grep reaches each one in one hop. The site behind a shared helper (public list to `getBookmarkTitle`) was found by its function name.

So "large" (160k lines) is not enough on its own. Size only helps when the symptom does not give away the code shape. Untried so far: symptoms that only reproduce through a real browser or a worker process (no in-process test path); causes in config, generated code or migration SQL instead of TS; two plants where fixing the obvious one hides the second. If staff do not ask for difficulty, ship tasks like these: they are fair and quiet, and planting plus screening took about 30 minutes each on a repo with a fast API test suite.

### Chain restoration round (Nov 15 night): depth 8 did NOT make it hard either

I tested recipe C1 from the playbook's making-tasks-hard.md on the same Karakeep repo, in `~/Hackathons-local/frist/chain-task/`. The flow was collaborative lists, in 8 dependent steps: invite by email; the owner's Manage collaborators dialog; the invitee's Pending invitations card; accept, decline and revoke; the shared list showing up with its role and Has collaborators flag; reading it with the owner's private state hidden; role permissions; and role change, remove and leave, where that person's bookmarks leave with them.

- **d4:** the logic of steps 1 to 4 was removed.
- **d8:** the logic of all 8 steps was removed, across 4 model files: invitation bodies, the collaborator branch of the list loader, shared-list lookup, privacy hiding, the collaborator-aware filters, the role tables, and the membership mutations.
- **Both:** quiet (tsc, oxlint, oxfmt and the 472 visible tests stayed green). The ticket was the same for both: one Frist-style "half-built" feature listing every rule and exact error message. The screen was 561 tests: the original's 87 collaboration tests plus an end-to-end journey. The original passed it 3 times.

| Variant | Opus 5.5 screen | Screen result |
|---|---|---|
| d4 | 3.0 min, $1.04 | 560/561. The one miss was our ticket's fault: it said hidden emails are "empty" and the solver returned `""` instead of `null` |
| d8 | 4.2 min, $1.32, 24 tool calls | 561/561 |

Both transcript audits were CLEAN. d8 was solved in under 10 minutes, so I made no extra runs. How it went:
1. One grep of the feature nouns (`collaborat|invitation`) listed every masked file. The solver then read the 4 model files in full (about 3,000 lines) in 10 calls, before editing anything.
2. On a missing feature, the half-built code is where it starts. Stub bodies, owner-only branches and the schema (the membership cascade column) show where each rule goes. The full ticket then supplies every rule. The cross-step trap (pass the membership id so leaving removes that person's bookmarks) was found by reading the schema.
3. The solver wrote one end-to-end vitest over the whole journey, fixed what it showed, and deleted it. A fast in-memory test suite makes re-walking the chain cheap, so effort does not fall off with depth the way ProgramDistill reports for browser journeys.
4. Ticket lessons:
   - Say `null`, not "empty".
   - State both errors for adding someone else's bookmark: one they cannot see gives "Bookmark not found"; one they can see but do not own gives "User is not allowed to access resource".

So depth alone does not make it hard when every step lives in the API layer, one noun-grep finds every site, and a fast test suite can replay the whole chain. ProgramDistill's drop came from browser-journey replay, where re-walking is slow. To get C1's effect, put the chain's state across layers that have no in-process test path (UI state carried between pages, a worker, a reload), not in more server functions.

### Browser-only chain round (Nov 15 night): client-side state did NOT make it hard either

I tested the hypothesis from the chain round on the Quillstack clone (React/TS/Vite, about 2,700 lines), in `~/Hackathons-local/frist/browser-chain/`. I built a 7-step chain whose state lives only in the browser, then removed all of it: (1) the URL holds the view (project key, search, status, priority, labels, assignee, sort), restored on reload and pasted links, and a URL without a project gets one written in by replace; (2) the Board/List tabs and "My issues" carry the query; (3) Back/Forward, where each discrete change pushes and typing replaces; (4) a multi-select shared by Board and List, which drops issues a filter hides; (5) bulk Set status and Set priority with an Undo toast that restores each issue's own old value on the server; (6) saved views in localStorage, listed in the sidebar, where saving a name again replaces it; (7) delete a view. The backend stayed the same.

- **Broken copy:** filters held in memory (so they still work on the page), and the checkboxes and Save view button left inert. The repo had no tests, so the only check was a real browser. Typecheck stayed clean, and all 28 existing journeys stayed green.
- **Ticket:** a Frist "half-built" ticket that lists every URL parameter, label, toast text and history rule.
- **Grader:** 12 held-out Playwright feature journeys plus 28 regression journeys, with a fresh database per journey. The reference passed 40/40 three times. The broken copy passed 28/40 three times (every feature journey failed, every regression passed).

| Solver | Result |
|---|---|
| Opus 5.5, one headless run (Playwright allowed) | solved 40/40 in 6.8 min wall, $1.58, 29 turns, audit CLEAN |

It was solved in under 10 minutes, so I made no extra runs. How it went:
1. Two `cat` calls read the whole frontend. The solver then wrote the entire feature in 5 edit calls, before running anything.
2. It booted the app on its ports and wrote one Playwright script that walked the whole chain (filters, reload, tabs, Back, selection, bulk with Undo, saved views). It found the one real snag by screenshot: the precompiled CSS ignores new Tailwind classes, so the bar rendered off-screen. It fixed that with inline styles and reran.
3. A browser replay of a 7-step journey takes about 30 seconds when the solver scripts it. That makes it nearly as cheap as an in-memory test, so ProgramDistill's slow-replay effect never shows up. Their agents walk the browser click by click, and ours can script it.

So client-only state plus browser-only verification is not enough on a small app with a fully specified ticket. The ticket has to list every rule to be fair, and a solver who reads all the code turns that list into code in one pass. What is left to try: a solver limited to pixel actions (as in FristWorld), or a large generated frontend where the state plumbing cannot be read in two calls.

## Difficulty calibration

- **Screen (record, do not block).** Right after the bug author finishes, run one headless Opus solver on the ticket + broken repo (command in `../SKILL.md` "Pipeline" step 2) and grade it with the private `screen_check.sh` the bug author writes (one line per planted cause, FIXED/BROKEN). It runs in parallel with the test, wrong-fix and hack authors. Write the result on BOARD.md and submit correct, well-tested tasks even when Opus solves them; only when staff or a rejection say difficulty matters does a quick solve mean harden first. Make the screen compare per-member facts, not array order (one screen reported a false failure on split order). The screen counts as solver attempt 1 when the repo and ticket do not change afterwards.

- **Solvable:** a strong solver (fresh agent, ticket + broken repo, no tests) passes at least once in K runs. If 0/K, read the failures: divergent interpretations mean the ticket is ambiguous (fix the ticket); valid fixes rejected mean tests over-fit (add an alt fix, loosen facts); same wrong fix repeatedly is a genuine difficulty (keep, it is a "real reason" failure Frist values).
- **Not trivially marked:** no greppable marker, crash, or type error (see "Bad" in the taxonomy). Beyond that, solve speed is recorded, not gated, until staff say otherwise; hardening levers are above.
- **Target band (only if staff ask for difficulty):** pass rate strictly between 0 and 1 across solvers (SWE-smith-style training sets keep instances with mixed rollout outcomes; e.g. SWE-Master uses 3 to 12 rollouts, https://arxiv.org/abs/2602.03411, search summary). PROPEL calls this the "learnable frontier". https://arxiv.org/abs/2606.18284
- **Static predictors:** difficulty is mostly patch fragmentation and repo scale (AUC 0.863). https://arxiv.org/abs/2608.18280 . So a fix spread over 2 to 3 files on a big clone is harder than a one-liner, without any ambiguity cost.
- **Hackathon budget:** K=1 (the screen) by default; 2 Opus + 2 Fable only when staff say difficulty matters. SWE-smith found difficulty barely changed training value, so do not over-tune; just avoid the trivially marked and the unsolvable.

## Pipeline: one clone, many tasks

Serialized, once per clone (first 30 to 45 minutes after the clone is done):
1. **Catalog agent:** journeys + 15 to 30 scored bug sites (table above), split across feature areas.
2. **Harness agent** (prompt 0b in role-prompts.md): one shared fact recorder and journey runner (Playwright) with `MB_SLOT` ports, fresh DB per run, anchored clock, ships inside hidden_tests. Every task reuses it, so later tasks only write journeys and inputs. This is the biggest throughput win.

Per task, one sandbox per role (see "Isolation" in role-prompts.md; physical dirs plus canaries plus a transcript audit), with an information firewall:

Run order is `../SKILL.md` "Pipeline". The firewall, by role prompt number in `role-prompts.md`:

| Prompt | Agent | Sees | Never sees |
|---|---|---|---|
| 1 | Bug author | original, catalog row, harness | tests |
| 2 | Test author | ticket, heldout_hint, reference copy, harness | bug diff, broken repo |
| 3 | Wrong-fix author | ticket, broken repo | tests, solution, reference |
| 3b | Hack author | broken repo, grading commands, hidden test file names | solution, reference, test contents |
| 5 | Solver screen (K=1 by default) | ticket, broken repo | tests, solution, reference, internet |
| 4 | Checker (mutation_bar + verify_task + isolation_check) | everything | (sends survivors back to the test author) |
| playbook | Reviewer + red-team (non-lazy-judges.md) | everything | |

Test author, wrong-fix author, hack author and solver screen run concurrently right after the bug author. The checker loops with the test author until `MUTATION BAR: PASS`. Serialize: edits to the shared harness, merges to the main clone, submission, and anything that starts a dev server when the machine is busy.

**Resource budget (learned the hard way, Nov 14).** On a 10-core laptop, 9 helper agents plus 4 parallel mutation bars (each starting a backend, a Vite server and Chromium) pushed the load average to 60 to 100 and nearly crashed the machine. Port collisions with unrelated processes then made the harness exit 3, which an earlier mutation_bar counted as kills. Rules:
- Playbook "Machine limits" apply: 3 to 5 concurrent workers at most, counting every agent that boots a server, a browser or a mutation bar; keep the 1-minute load under 12; drop to 2 if it climbs. `nice -n 15` on installs, builds, test runs and mutation_bar; `--jobs 1` (one dev server and one browser) unless the machine is idle, never more than 2.
- Check `uptime` before each batch and wait while the 1-minute load is 12 or more.
- Give every concurrent run its own port range (`MB_PORT_BASE`, `--slot-base`); the harness must exit 3 on a busy port, and mutation_bar reports exit 3 as UNGRADED, never as a kill.
- Solvers are cheap (1 to 2 minutes of tool time each on a single-file bug); hidden-test authors are the slow step (18 to 20 minutes each).

Measured clock on a real app (Nov 14 dry run, cold start, three tasks in parallel): catalog 8 min and harness 16 min in parallel; bug author 10 to 12 min; test author 18 to 20 min, wrong-fix author 9 to 18 min and solver 1 to 2 min, all in parallel; mutation bar 5 to 15 min per suite when run one candidate at a time. That is about 60 minutes from finished clone to three graded tasks when the machine is not overloaded.

## Likely rejection causes ([INFERRED] unless marked)

1. Original fails a hidden check or flakes (time, ports, order, shared DB). Frist states "the original code passes every task" [VERIFIED].
2. Broken app passes (bug not on the tested path) [VERIFIED rule].
3. Valid fixes rejected: tests pin incidental details or one implementation. Use alt fixes.
4. Wrong fixes accepted: example-only tests. Use goldens on held-out inputs.
5. Ambiguous ticket, or ticket naming files, functions or the cause [VERIFIED Frist style].
6. Trivial: greppable marker, crash with stack trace, type error, one obvious line.
7. Broken start: regression journeys red on the broken repo.
8. Near-duplicate of another submitted task (same site or same bug type on the same page).
9. Template or metadata mismatch with Frist's format.
